# RF-DETR 首次真实 CPU 检查：原始严格加载失败，资源已闭合

2026-11-07。这是一次已实际执行的接口检查，不是 SAR 精度实验。

主训练在 33,536 次更新被严格接受后，Root 单独执行一次 CPU 原结构 Nano312 检查。原工具、SSH、子进程均返回1；没有超时或自动重跑。外部严格进程观察、来源字节复核及资源闭合通过后，原主训练接续至下一段。这个失败保留为失败，不以收尾工具返回0替换原始非零。

实际已导入 Torch、安全读取官方权重并构造模型，随后 `load_state_dict(strict=True)` 报告唯一缺键 `_kp_active_mask`，因此没有执行前向。另记录一次被阻断的 `socket.bind`；原检查未记录调用栈，不能仅凭后续源码把实际来源认定为已证明。

根因审阅发现，官方固定版本 [weights.py:195–228](https://github.com/roboflow/rf-detr/blob/639eac4555ceb89ef399ccda3fde716bbcfe34cb/src/rfdetr/models/weights.py#L195) 已明确把该键解释为按 keypoint schema 重建的确定性缓冲，而非学习参数。[lwdetr.py](https://github.com/roboflow/rf-detr/blob/639eac4555ceb89ef399ccda3fde716bbcfe34cb/src/rfdetr/models/lwdetr.py#L253) 对空 schema 构造 bool 的0×0缓冲。我们的首个检查要求旧原始 state 与新版 schema 直接完全相同，未采用该官方说明的兼容路径；这是接口验证设计需修正的范围，**不能判定RF-DETR方法失效**。

实际安装的 urllib3 源码还存在导入时 `_has_ipv6('::1')` 的loopback端口0绑定探测，并吞掉异常；requests会导入urllib3。这是一次bind记录的强静态解释，原尝试缺栈，故仍保留实际调用来源未确认。所有实际绑定都被旧审计钩子事前阻断。

后续只准备新的、明确命名的兼容候选：仅当缺键集合严格为该单键、keypoints关闭且目标缓冲确为CPU/bool/0×0/零元素时，补入其独立空副本，再对完成后的schema做严格加载和原始全部Tensor逐项等值验证；不改原checkpoint，不放宽其他缺键，不把结果称为原始state直接strict通过。网络检查保持事前阻断，仅增加实际调用栈、地址及源码匹配来区别确定的能力探测和其他尝试。该候选尚未执行，需新的独立原任务与资源资格；旧原始失败不升级。

没有新SAR预测、AP、机制增益、SOTA或TGRS就绪结论。当前优先让原长训继续，下一模型检查只在完成指定修正及来源/资源条件后进入。

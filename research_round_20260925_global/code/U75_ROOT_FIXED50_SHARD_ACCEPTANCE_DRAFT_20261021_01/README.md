## Public interface and scope

`accept_shard(spec_ref, original_terminal, postcheck, *, closed)` returns a
self-contained metadata proof only after checking the supplied external facts
and actual callback-provided bytes. `postcheck` is an explicit file ref to the
original independent external post observation JSON. `closed(ref)` must return
the same actual file path with a binary `open('rb')` interface. The helper hashes
the complete bytes itself. For a real `Path` it also requires the path to be
absolute, canonical and not a symlink. It does not translate host paths.

The intended future location for reading DGX POSIX inputs is a separate DGX
stdlib-only external post/acceptance task. A Windows Root process cannot pretend
`Path('/home/...')` is the DGX file. Root may explicitly stage byte-exact original
SSH stdout/stderr as new readable evidence artifacts, retaining the original
capture and transfer relationship privately. These are original raw stream
bytes, not reconstructed or reserialized equivalent logs. No real host, account,
key path, Ops path or deployment address is hardcoded here.

`validate_accepted_proof(proof, prediction)` performs pure metadata consistency
checks and is reusable by the separate U76 four-shard gate. Its caller must
first verify the original proof and full prediction raw bytes against their
explicit refs. It cannot infer the genuine origin of Root observations from
JSON. A fabricated fixture or a caller's `root_accepted` flag supplies no actual
execution evidence. Root still must provide original facts from real tools and
preserve their raw evidence. Future Root invocation, persistence/CAS, accounting
and the CPU prelaunch gate are not implemented or executed by this helper.

The proof schema is `Root-U75-DGX-fixed50-shard-accepted-v1`, with status
`ROOT_ACCEPTED_SINGLE_SHARD_PREDICTION`. `root_accepted=True` means Root has
received that prediction shard within this narrow scope when invoked using
genuine facts. `qualified=False`, `AP=False`, `TEST=False`, `new_training=False`
and integer training credit zero remain: this is not CPU evaluation, complete
runtime ABI, academic quality, paper readiness or a whole-population result.
`DEV` and `DEV_technical_input` are true because the shard reads DEV inputs.

## Independent terminal and post facts

The exact eleven original-terminal fields are:

`root_observed_tool_exit_code`, `root_observed_tool_chunk_id`, `SSH_returncode`,
`owner_process_exit_code`, `original_exec_wait_observed`, `command`, `stdout_ref`,
`stderr_ref`, `attempt_id`, `phase`, `spec_ref`.

All three external exit codes must be actual integer zero, not `False`, unknown
or a planned value. The command must be exactly the argv representation of
`exec <actual interpreter> -u <pinned owner> --spec <actual spec> --spec-sha <SHA>`.
The interpreter comes from the original receipt, not a new guessed executable;
the existing U74 Python runtime gate remains. No shell wrapper or extra command
is accepted. This does not claim complete Python binary/shared-library closure.
The original synchronous exec/wait mapping must actually have been observed by
Root before an SSH zero can support the owner OS zero. `controller_returning`
inside the owner JSON never substitutes for this external observation.

The independent post JSON has exactly seventeen fields: its own Root tool zero
and chunk; the same spec, phase and attempt; the entire original-terminal object;
the original boot, owner and child identities; both current identities; both
original-birth absence flags; a resolved empty original owned-group scan; the
all-owned-processes-absent flag; and five actual output refs. Its tool chunk must
differ from the original numerical terminal chunk. Same PID with the same birth,
unknown/failed scan, reboot, a different attempt or reused terminal is rejected.
Original child parent/session/PGID/startticks must match the actual owner receipt.

Root must observe the collector's real tool terminal before encapsulating that
post fact. A still-running collector cannot self-write its own future tool zero
or chunk. The original numerical terminal, independent collector terminal and
subsequent encapsulation/persistence task are distinct. The helper neither
collects nor manufactures any of them.

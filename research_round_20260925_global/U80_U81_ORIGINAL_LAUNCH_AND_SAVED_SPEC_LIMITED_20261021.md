# U80—U81：原执行器与已保存配置消费的有限记录

本备忘只记录普通未绑定源码和有限合成验证，不记录训练结果。这些新增入口未实际执行 SSH、远程进程探测、完整 E50 预测或 CPU 评价，没有 AP 或发表级结论。源码能调用原执行器，不等于原执行器已经运行，更不等于后续接收成立。

U80 rev01 暴露三个具体缺口，原件完整保留。第一，等待本机 SSH 子进程异常后，未有界清理并回收该自有句柄，可能遗留本机进程；不能据此推断远端已结束。第二，远程字节预检只确认 CPU0/1 可用，没有实际设置并回读预检进程的亲和性与较低调度优先级。第三，本机读取将原引用与 as_posix 输出整字典比较，和 U78 在 Windows 保存时返回的 str(Path) 引用不兼容；相同实际文件、字节数及 SHA 仍会被拒绝。

独立 rev02 仅修这三个边界：异常时对自己的本机 Popen 句柄有界清理、等待回收，保留原异常和远端未知状态；字节预检实际设置并核实 CPU0/1、nice≥10；本机读取先核规范路径身份，再核原字节数与 SHA，保留传入整引用，不放宽远端 POSIX 和 Source 约束。三个新增针对性测试的 RED 为 `3193ef`、`b4099a`、`89b9e3`，最终选中三项 `e101d8` 退出零，差异检查 `436a4a` 退出零。这里复述作者工具记录，未复跑旧套件。

U81 消费 U78 实际保存的 SPEC、ADMISSION、PREPARATION 原字节与整引用，核原请求、真实准备工具终态、CPU 请求摘要、四证明的原顺序及同一完整端点，再调用原 U71 元数据校验与固定共享 CPU 启动函数；不重新拼 SPEC。真正共享实现的联调先在 rev01 出现 `0c6819` 失败，准确暴露上述 Windows 引用问题；不归一化原引用，仅换为 rev02 固定源码后，同一路径 `81df0e` 通过。五项 U81 新测试 `136122` 退出零，静态检查 `1ae057` 退出零。

测试仍有明确边界：隔离用例使用微型启动替身，真正共享用例执行固定 U80 定义，但传输、子句柄及权威文件均为临时合成材料。它验证了中途前缀或少一个已提交分片拒启动，以及合成合法情形的预检、启动调用、wait 和二进制日志保留；不是实际 SSH 或资源资格。生产没有测试中的临时 pin 豁免。

共享入口在 owner 启动前先保存 attempt 并将 scoped active 状态写入权威文件；断线或等待未知不能自动清活跃、认证全体进程回收或自动重发。CPU 必须由 U81 消费本次保存配置后进入共享 API，U80 自身 CLI 不直接开放 CPU 路径。真实GPU和CPU启动均要求当前权威状态空闲、已接受的 FORMAL37050；CPU另外要求四条原证明／预测整引用一致。启动返回、工具终态、独立 post 和 U79 接收是不同事件；源码完成不替代这些实际观察，最终 CPU／AP 接收也未执行。

部署还有限制：Root 的 Windows D 盘保存引用与 `/home/...` Source 混合存在，默认同主机 CLI 不能称为即用。可信 Root API 可以按有限显式 `OriginalRef → canonicalLocalCopyRef` 清单读取控制材料，逐一核同字节数和 SHA，拒缺项、冲突及未声明读取；这只是运输，不替换 SPEC 内原 Source 身份，也不为数据、CP、库建立隐式镜像。该操作层尚未真实部署，须在实际 E50 启动前落实，不因此扩 CLI 或新增框架。
